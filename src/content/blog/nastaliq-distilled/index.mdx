A previous post introduced the [NeuralType (.ntf)](/blog/neuraltype) font format concept: a font can be a small neural network, instead of a system
that emulates Gutenberg's movable type in virtual
rectangles. The first .ntf font was
[square Kufic](https://en.wikipedia.org/wiki/Kufic#Square_Kufic), a
style that looks like pixel art. That is easy to write off as a
neat trick, but this post makes the case that a neural network based font can do the
work of a real OpenType font and more.

I converted a standard OpenType font into a neural network based font, in one
of the styles that OpenType serves worst, Nasta’liq. The font I
used is [Gulzar](https://github.com/googlefonts/Gulzar), an OFL
licensed Nasta’liq by Borna Izadpanah, Fiona Ross, Alice Savoie, and
Simon Cozens. The early result is in the interactive demo below. Type, copy, paste, move the cursor with the arrow keys, and press space to separate joined letters.

<NeuralTypeDemo {...nastaliqDemo} />

The demo above runs the full pipeline in your browser. The font is
a model with 1.36 million parameters, stored as a 5.4 MB .ntf file.
The engine is Rust compiled to WASM, mostly built with
[Linebender](https://linebender.org/) crates. It runs the model, places each
letter in the cascade, and traces the contours.

NeuralType is a general format, and Nasta’liq is one use case
among many. I am using it for the early demo fonts because it makes
the strongest case.

Distillation is the test. If the distilled font matches its
teacher, the format works. It also answers a basic question early:
how many parameters does Nasta’liq need? After that, the goal is
new fonts, designed for the format, that render the script in a
form true to the manuscript and calligraphy tradition it comes
from.

Nasta’liq is a cursive, flowing style. Letters join or break by
the rules of the Arabic script, and a word is a chain of connected
runs. Within a run, each letter hangs below the letter before it.
A long run starts high above the line and steps down until its
last letter lands on it.

In handwriting there is no baseline grid. The line a word sits on
can be straight or curved, and letterforms, dots, and swashes move
freely around it to fill the space. OpenType approximates all of
this with more than one thousand glyphs and cursive-attachment
rules. Even so, no OpenType Nasta’liq font has come close to the
style as it developed in manuscript and calligraphy culture.

![A calligraphic composition by Mishkín-Qalam.](./mishkin-qalam-48.jpg)

### The Distillation Process: Measuring Gulzar

The first step is to measure the problem: how much contextual
behavior does Gulzar contain?

We shaped every two-letter word through Gulzar with
[harfrust](https://github.com/harfbuzz/harfrust) and counted how
many different glyphs each letter takes at the start of the word.
The count depends on the letter that follows. ن is drawn with 16
different glyphs, ي with 15, م with 14. Across all 31 letters,
Gulzar uses 344 distinct word-initial glyphs. Amiri, a naskh with
rich contextual behavior, uses 150 on the same test.

The figure below shows word-initial ن in green, with the following
letter in gray. The follower selects the shape.

![Fourteen ordered pairs. The green word-initial ن takes a different shape for each gray follower.](./noon-variants.png)

Counting glyphs measures one half of the problem: how many shapes
there are. The other half is how far words climb. The shaped word
نستعليق places glyphs at vertical offsets up to **1.38 em above the
baseline**. One word spans more than a full em of vertical travel.
That geometry strains the metal-type box that digital font formats
still emulate. Numbers like this are why we are trying a new format.

The figure below shows the shaped word نستعليق. The letters
alternate green and gray, the red chain joins the letter origins, and
the gray rule is the baseline.

![The word Nasta’liq shaped by Gulzar: letters step down from high above the baseline, and the final swash lands below it.](./cascade.png)

### Extraction

Distillation needs a teacher: a working system whose output the new
model learns to copy. Here the teacher is not the Gulzar font file
by itself. It is Gulzar plus HarfBuzz, the shaping engine that reads
text, consults the rule tables in the font, and answers: these
glyphs, at these positions.

The same text always shapes to the same result, and shaping a word
takes a fraction of a millisecond. So training data can be
generated in any quantity.

The extraction tool (`crates/neuraltype-distill`) shapes every
short word: every single letter, every two-letter word, and every
three-letter word. That is 30,783 small words. The three-letter
words matter because they are the shortest text where a letter has
a neighbor on each side. Those neighbors produce the medial forms,
the shapes a letter takes in the middle of a word. A second pass
added 24 real words: the bismillah, Al-Fatiha, Al-Ikhlas, and
نستعليق. The full corpus is 30,807 words.

This corpus is also why unseen words in the demo render rough. A
longer word contains letter contexts that no short word ever showed
the model, and there it has to guess. The fix is a larger corpus,
built from real Urdu and Persian text.

For every letter in every word, the tool records two facts. The
first is the composed shape: the base letterform and its dots, as
one unit. The second is the offset from the previous letter: how
far across, and how far down. Following the offsets letter by
letter rebuilds the downward cascade of the word.

The dataset holds 91,390 letter-in-context records, 416 unique
glyphs, and **1,150 unique composed shapes**. More than 100 of those
shapes belong to خ alone. Between adjacent letters, the cascade drops
as much as 1.66 em.

The figure below shows every composed shape of خ in the dataset, 108
in total.

![All 108 composed shapes of خ in the dataset, in a grid.](./kha-shapes.png)

One measurement set the size of the model's input. Given a letter
and two neighbors on each side, Gulzar always draws exactly one
shape. So a five-letter window captures everything this teacher
knows.

That number measures Gulzar, not the goal. A calligrapher is aware
of everything: the whole word, the line, the space on the page. A
neural font can grow toward that by taking more of the text as
input.

### Shapes as Fields

Extraction leaves us with 1,150 shapes, stored as bézier outlines.
The model has to learn to draw these shapes. In what form should
it output them?

An outline is a list of curve points, and the list has a different
length for every shape. That is hard for a small neural network:
get one point wrong and the whole contour breaks. A neural network
learns best when the output is a fixed grid of numbers, where a
small change in the weights makes a small change in the picture.
So we do not ask the model to write curves. We ask it to paint a
picture that curves can be recovered from exactly.

We render each of the 1,150 shapes to a signed-distance field. It
looks like a soft grayscale image of the letter, but the gray means
something different. In an ordinary image, each pixel says how much
ink is at that spot, and pixels away from the letter's edge say
nothing useful. In a signed-distance field, each cell holds the
distance to the nearest edge of the shape: positive inside, negative
outside. Every cell knows where the edge is, even cells far from
it.

The outline of the letter is the line where the field crosses
zero. Because the field changes smoothly, that line can be found
between cells, at finer than pixel precision. A small error in the
model's output nudges the edge slightly instead of punching a hole
in the letter. The field is the continuous version of the binary
grid in the first NeuralType font: figure and ground, with no
stroke or skeleton assumptions.

The image below shows the isolated خ from the training set. On the
left is the shape. On the right is its signed-distance field, with
the zero contour in red. The model learns to paint the picture on
the right.

![The isolated خ from Gulzar, and the same shape as a signed-distance field with the zero contour marked in red.](./sdf-kha.png)

The figure below zooms in. The red box marks a small patch of the
field, shown cell by cell on the right, each cell printed with its
distance in pixels: negative outside, positive inside. The red line
is the outline, drawn where the values cross zero. Reading
neighboring cells places that crossing at a fraction of a pixel,
which is how a coarse grid still yields a precise edge. This patch
crosses a thin stroke, so two edges pass through it.

![A patch of the distance field enlarged to a grid of numbered cells. Values rise from negative to positive and back, and the red zero contour passes between the cells at interpolated positions.](./sdf-cells.png)

We rendered test shapes at two resolutions. At 64 pixels
per em, the tapers and hairlines of Gulzar survive the threshold. At
96 pixels per em, the result looks the same at reading size, but the
model must output 2.3 times more pixels. So the resolution is 64. The
shared canvas is 155×219 pixels. The canvas is large because Nasta’liq
is large: swash tails and dots extend far from the origin of each
letter.

Below is the isolated خ at both resolutions, shown at the same
size: 64 on the left, 96 on the right.

![The isolated خ thresholded at 64 and 96 pixels per em, at the same size. The two are nearly identical.](./res-64-96.png)

### Training the Student

The model is small, and it works in three steps. First, each of the
five context letters comes in as a learned code, a short list of
numbers the model chooses for each letter during training. Second, a
small network mixes the five codes into one description of the shape
to draw: 256 numbers. Third, a stack of five upscaling layers turns
that description into the field, doubling the size of the picture at
each step. A separate small output predicts the offset to the next
letter.

The total is 1.36 million parameters, 5.4 MB stored as 32-bit
numbers. The Gulzar TTF is 963 KB.

The model card:

| Nasta’liq-gulzar .ntf, v0 (working name) |   |
| --- | --- |
| architecture | 5 context embeddings (24 dims) → MLP (120 → 256) → 5 transposed convolutions (128 → 64 → 32 → 16 → 8 → 1 channels, 4×4 kernels, stride 2) + a 2-value displacement head |
| parameters | 1,357,995 |
| file | 5,433,100 bytes: f32 weights + a 1.1 KB JSON header |
| output | one 155×219 signed-distance field at 64 px/em, plus one displacement vector |
| vocabulary | 34 tokens: 31 letters, the لا and لله ligatures, and a boundary token |
| corpus | 30,807 words from the teacher: 91,390 letter-in-context records, 1,150 composed shapes |
| teacher | Gulzar Regular shaped by HarfBuzz ([harfrust](https://github.com/harfbuzz/harfrust)) |
| optimizer | AdamW, lr 3e-4, then a 1e-4 decay pass; batch 128; every 20th record held out |
| compute | one Apple M4 Mac laptop, CPU ([candle](https://github.com/huggingface/candle) accelerate backend), about 8 minutes per epoch. Later runs moved to a Linux PC with an RTX 2060 SUPER, at 100 seconds per epoch |

Training runs in [candle](https://github.com/huggingface/candle), so
the same code trains on CPU, Metal, or CUDA. Inference, running the trained model to generate a
letterform, is plain Rust in the engine, with no machine-learning
framework. A .ntf file is only weights, and running weights is only
arithmetic.

Progress is measured with IoU, intersection over union, the
standard score for shape agreement: the area where the model's ink
and the teacher's ink overlap, divided by the area covered by
either. Identical shapes score 1.0, and shapes with no overlap
score 0.

Words were legible by epoch 12. Thin strokes form last. The training loss explains why: a hairline
is worth tens of pixels and a bowl is worth thousands, so the model
gets the bowls right first.

The hardest word was الله. Gulzar draws it with a dedicated
ligature, and no word in the first corpus was long enough to trigger
it. Adding the bismillah and other real words put the ligature in
the data, but a few dozen words in a corpus of thirty thousand learn
slowly. The fix was to repeat those words dozens of times per epoch,
and the ligature converged in eight epochs.

Training finished at an IoU of 0.945. A final pass with a decaying learning rate settled the last details,
the same schedule that took the Kufic font from almost correct to
exact. The bismillah now renders better, ligatures included.

The sheet below compares the teacher with the final model. Gulzar is
gray on top. The model is green below.

![The bismillah words, نور, and نستعليق rendered by Gulzar in gray above, and by the final model in green below. The rows match, including the الله ligature.](./teacher-model.png)

### Tracing with img2bez

The model outputs a field, but text needs outlines. The demo uses
two tracers. While you type, a fast sub-pixel tracer draws each word
with no added latency. When input settles, each word upgrades to a
quality outline from [img2bez](/blog/img2bez), the autotracer I
built for turning rasters into font-grade bézier curves.

The upgrade runs in a Web Worker, a background thread the browser
provides. The slow tracing never runs on the thread that handles
typing and drawing, so the editor stays responsive. Each word's
outline swaps in when it is ready.

Working on the .ntf pipeline added one new ability to img2bez: it
now traces the model's distance field directly, with no image step
in between. The curves it fits are smooth everywhere, with no
corners or kinks. No raster image exists anywhere in the render
path: the model paints a field, and the field becomes curves.

### Making It Bigger

The model in the demo is 1.36 million parameters. The obvious next
move was a bigger model. We tried three versions of bigger, and all
three came out worse, each for a different reason.

**More pixels.** Retraining at 96 px/em grew the model to 3.10
million parameters, and the letters looked the same. Almost all of
the new parameters went into the one layer that seeds the larger
picture, not into knowledge of the letterforms. And resolution was
never the limit: a distance field at 64 px/em already places an
edge at a fraction of a pixel.

**Wider layers.** Doubling the width of every layer gave 5.36
million parameters and a worse score: 0.809 against the small
model's 0.945, with heavy strokes and letters merging where they
should stay apart. The problem was not size but a borrowed recipe:
it trained with the same settings as a model a quarter as large,
and settings do not transfer across model sizes
([hyperparameter transfer](https://arxiv.org/abs/2203.03466)). Its
score was still climbing when the run ended.

**Outlines instead of fields.** The third attempt predicted curve
points directly as a stream of drawing tokens, with a 12.7 million
parameter transformer, in the same spirit as the
[Virtua Grotesk](/blog/virtua-grotesk) model. It never learned to
draw. Dots land near where dots belong, and fragments follow the
downward slope of the words, but strokes never close.

![Three words. The teacher's outlines on the left, the field model in the middle drawing them almost identically, and the vector model on the right producing only small scattered fragments.](./vector-fragments.png)

| | parameters | file | result |
| --- | --- | --- | --- |
| field, 64 px/em | 1,357,995 | 5.4 MB | IoU 0.945, the font in the demo |
| field, 96 px/em | 3,101,483 | 12.4 MB | IoU 0.825, no visible gain |
| field, 64 px/em, wide | 5,357,091 | 21.4 MB | IoU 0.809, strokes merge |
| vector, outline tokens | 12,693,639 | 53.3 MB | accuracy 0.482, fragments |

The smallest model is still the best one, but it is not finished.
At an IoU of 0.945, visible detail is lost: compared to the
teacher, sharp features are rounded, and small features are
weakened or missing. Smooth curves are acceptable, and matching
OpenType exactly is not the goal, but the lost detail must be
recovered before the model can be considered complete. None of the
three attempts addressed this gap.

The vector failure matches the published record.
[DeepVecFont](https://arxiv.org/abs/2110.06688) generated outlines
as command sequences and needed image-guided refinement to produce
usable curves; [DeepVecFont-v2](https://arxiv.org/abs/2303.14585)
redesigned the outline representation to make the sequences
learnable at all; and
[VecFontSDF](https://arxiv.org/abs/2303.12675) moved vector font
synthesis onto signed distance functions, the representation this
project already uses.

The next steps are about information, not parameters. First, extend
the corpus to real Urdu and Persian text. Second, keep the
teacher's variants: where Gulzar draws the same context more than
one way, the training set currently keeps only the most common
shape, so the model is trained on an average of different letters.
Third, after the data, test representations that store more shape
per parameter, such as a model that returns the distance value for
any queried point instead of a fixed grid of samples.
