A previous post introduced the [NeuralType (.ntf)](/blog/neuraltype) font
format. An .ntf font is a small neural network, not a system that emulates
Gutenberg's movable type with virtual rectangles. The first .ntf font was
[square Kufic](https://en.wikipedia.org/wiki/Kufic#Square_Kufic), a
style that resembles low-resolution pixel art. That font was a simple test just to see if the concept could work.
This post tests whether a neural font can reproduce a complex OpenType font and be a real alternative to to Opentype format.

I converted [Gulzar](https://github.com/googlefonts/Gulzar), an OpenType
Nasta’liq font, into a .ntf. OpenType handles Nasta’liq poorly so this seems like a good style to use for exploring this concept. The current
result is in the interactive demo below. Type, copy, paste, move the cursor with the arrow
keys, and press space to separate joined letters.

<NeuralTypeDemo {...nastaliqDemo} />

The demo runs the full pipeline in the browser. The font has 1.36 million
parameters and takes 1.38 MB. The engine is Rust compiled to WASM and built
mostly with
[Linebender](https://linebender.org/) crates.

Distillation of existing OpenType fonts tests whether the format works. It also gives early estimates of the required parameter count and file size. The longer-term goal is to design
new fonts for the format that can do things OpenType cannot.

Nasta’liq is a relativly non-linear style of the Perso-Arabic script. In
calligraphy form, composition if relativly freeform. A calligrapher can stack words, extend strokes, and adjust the positions of letters and dots to balance the black and white space.

![A calligraphic composition by Mishkín-Qalam.](./mishkin-qalam-48.jpg)
<p class="img-credit">Calligraphy by <a href="https://en.wikipedia.org/wiki/Mishk%C3%ADn-Qalam">Mishkín-Qalam</a> (1826–1912). Public domain, via <a href="https://commons.wikimedia.org/wiki/File:Mishkin-Qalam-48.JPG">Wikimedia Commons</a>.</p>

An OpenType Nasta’liq font turns these choices into predefined glyphs and
shaping rules. OpenType can select contextual forms and move each glyph in both
axes, so it can reproduce the descending connections. But OpenType shaping does
not make new compositional decisions from the outlines or the available page
space. The font designer must anticipate contexts and encode the alternatives,
positioning, and collision fixes.

### Measuring Gulzar

The first step is to measure the problem: how much contextual
behavior does Gulzar contain?

I shaped every two-letter word in Gulzar with
[harfrust](https://github.com/harfbuzz/harfrust) and counted how
many glyphs each letter uses at the start of a word. The form varies with the
following letter. Gulzar uses 16 initial forms for ن, 15 for ي, and 14 for م.
Across all 31 letters, it uses 344 distinct word-initial glyphs. Amiri, a Naskh
font with rich contextual behavior, uses 150 in the same test.

The figure below shows initial ن in green, with the following
letter in gray. The follower selects the shape.

![Fourteen ordered pairs. The green word-initial ن takes a different shape for each gray follower.](./noon-variants.png)

The figure below shows the word نستعليق shaped by Gulzar. Glyphs reach **1.38 em above the baseline**. The word spans more than a full em of vertical travel. The
letters alternate between green and gray, and the gray rule marks the baseline.
Each red dot is an attachment point where Gulzar places one letter relative to
the previous letter. The red line connects the points in writing order. The
model must learn the offset between each pair of points.

![The word Nasta’liq shaped by Gulzar: letters step down from high above the baseline, and the final swash lands below it.](./cascade.png)

### Extraction

Distillation needs a teacher, a working system whose output the new model can
copy. The teacher is not the Gulzar font file alone. It is Gulzar plus
HarfBuzz, the shaping engine that reads text, consults the font's rule tables,
and returns glyphs and positions.

The same text always produces the same result, and shaping one word takes a
fraction of a millisecond. The extraction tool can therefore generate as much
training data as needed.

The
[`crates/neuraltype-distill`](https://github.com/eliheuer/post-opentype/tree/main/crates/neuraltype-distill)
extraction tool shapes every one-, two-, and three-letter word, for a total of
30,783.
Three-letter words are the shortest strings in which a letter has a neighbor on
both sides. These contexts produce medial forms. A second pass added 24 real
words from the bismillah, the surahs Al-Fatiha and Al-Ikhlas, and the word
نستعليق. The full corpus contains 30,807 words.

The corpus also explains the demo's limits. Longer words can contain letter
contexts absent from the training data, so the model must guess and often
renders them poorly. A larger corpus of real Urdu and Persian text should
reduce these failures.

For each letter cluster, the tool records its composed shape and its position.
It records the first cluster's origin, then each later cluster's offset from the
previous one. These offsets are the red steps in the figure above.

The corpus contains 91,390 cluster records and **1,150 distinct composed
shapes**. The letter خ uses 108 of them.

The figure below shows all 108 shapes used for خ.

![All 108 shapes of خ in the dataset, in a grid.](./kha-shapes.png)

### Signed-Distance Fields

We convert the 1,150 composed shapes into signed-distance fields. This lets
the model predict a grid of numbers instead of a sequence of bézier drawing
commands.

A signed-distance field stores the outline more usefully than a grayscale
image. Instead of recording the coverage of each pixel, it records the distance
to the nearest edge. Values are positive inside the shape and negative
outside. The edge is where the values cross zero. These distances let us place
the edge between grid cells.

A [2007 paper from Valve](https://steamcdn-a.akamaihd.net/apps/valve/2007/SIGGRAPH2007_AlphaTestedMagnification.pdf)
used this representation to render sharp vector graphics from low-resolution
textures in the Source game engine.

The figure follows one horizontal row through خ. The red line in the left panel
marks the row. The middle panel plots its values. Each red dot marks a zero
crossing where the row passes through an edge of the letter.

The right panel enlarges one crossing. It falls between two cells, and its
position is calculated from their values. The outline is therefore not limited
to the grid. A small prediction error moves the nearby edge. It does not break
the rest of the outline. The renderer follows the zero crossings to recover the
bézier curves.

![Three panels: the خ distance field with a red slice line, the slice's values as a curve crossing zero at each stroke edge, and one crossing magnified to show the edge landing between two cells.](./sdf-slice.png)

The image below shows the isolated خ from the training set. On the
left is the shape. On the right is its signed-distance field, with
the zero contour in red. The model learns to reproduce this field.

![The isolated خ from Gulzar, and the same shape as a signed-distance field with the zero contour marked in red.](./sdf-kha.png)

The next figure shows a small patch of the field cell by cell. Each cell lists
its distance in pixels: negative outside and positive inside. The red outline
passes through the interpolated zero crossings. This patch contains a thin
stroke, so the outline crosses it twice.

![A patch of the distance field enlarged to a grid of numbered cells. Values rise from negative to positive and back, and the red zero contour passes between the cells at interpolated positions.](./sdf-cells.png)

We rendered test shapes at two resolutions. At 64 pixels per em, Gulzar's
tapers and hairlines survive the threshold. At 96 pixels per em, the result
looks the same at reading size, but the model must output 2.3 times more pixels.
The model therefore uses 64 pixels per em on a shared 155×219-pixel canvas.
Nasta’liq needs this large canvas because swash tails and dots extend far from
each cluster's origin.

Below is the isolated خ at both resolutions, shown at the same
size: 64 on the left, 96 on the right.

![The isolated خ thresholded at 64 and 96 pixels per em, at the same size. The two are nearly identical.](./res-64-96.png)

### How the Network Works

The extraction step has already narrowed the problem. The network does not have
to learn a language, recognize letters in an image, or discover how Gulzar
works. Each training record supplies a target letter, its nearby letters, the
shape Gulzar draws, and where Gulzar places it. The network only has to learn
the mapping between them.

The current model reads the target letter and up to two letters on either side.
This limit belongs to this distilled model, not to NeuralType. A lookup table
turns each letter into 24 numbers learned during training. The network combines
these numbers into a 256-number description of the target shape.

This description feeds two outputs. A small branch predicts the horizontal and
vertical step to the next shape. The main branch expands the description into
128 small 7×5 maps. Five upscaling layers combine and enlarge them until they
form one 155×219 signed-distance field.

![The current model in four steps: read the target and nearby letters, combine their learned values into a shape description, enlarge that description through five layers, then output a distance field and an x/y position.](./model-architecture.png)

The model is simple because the task is closer to compression than invention.
Gulzar and HarfBuzz always produce the same shape for the same extracted
context, and the corpus contains only 1,150 target shapes. The decoder can reuse
what it learns about strokes, curves, and dots across all of them. It does not
use attention, diffusion, or a language model. One pass through a few ordinary
layers produces each shape and position.

### Training the Student

Training starts with random weights, so the first predictions are wrong. For
each group of examples, the model predicts a field and a position. Candle
compares every field cell with Gulzar's field and compares the two positions.
It combines these differences into one error score, then adjusts the weights to
reduce that score. Repeating this process teaches one set of weights to produce
all 1,150 shapes.

![Training as a loop: compare Gulzar's target field with the model's prediction, measure the difference, adjust the network's weights, and repeat.](./training-loop.png)

We use [Candle](https://github.com/huggingface/candle) to train the model because
it provides tools in Rust and runs on CPU, Metal, or CUDA.

Progress is measured with intersection over union (IoU), a standard score for
shape agreement. It divides the overlapping ink area by the total area covered
by either shape. Identical shapes score 1.0. Shapes with no overlap score 0.

Training finished at an IoU of 0.945. Fine-tuning at lower learning rates
refined the remaining details.

The sheet below compares the teacher with the final model. Gulzar is
gray on top. The model is green below.

![Five words rendered by Gulzar in gray above and by the final model in green below.](./teacher-model.png)

The final model has 1.36 million parameters and takes 1.38 MB, compared with 963
KB for the Gulzar TTF. It stores the weights as 8-bit values. The same weights
take 5.4 MB when stored as 32-bit values. The precision controls in the demo let
you compare the 32-bit, 16-bit, and 8-bit versions.

The 8-bit output is close to the original. Some strokes and letter positions
shift. Quantization-aware fine-tuning may reduce these differences.

Further file-size reductions are possible. We have not spent much time on
optimization yet. One part of the model contains 84 percent of its weights. We
could replace it with two smaller layers, for example.

These numbers do not fully predict the size of a font designed for the NeuralType format. This
model spends its capacity copying Gulzar's 1,150 OpenType-derived shapes. A
native design could learn a smaller set of rules, but whole-line composition
could also require a larger model, which for a lot of use cases would be worth the extra file size. The native square Kufic prototype is 215 KB,
but it is much simpler than Nasta’liq. About 1 MB is a reasonable target for a
native Nasta’liq font, and even up to 5-10MB would be worth it for something not possible in other formats.

The model card:

| `gulzar-int8.ntf` | |
| --- | --- |
| size | 1,380,371 bytes |
| parameters | 1,357,995 |
| output | one 155×219 signed-distance field at 64 px/em, plus one x/y position |
| coverage | 31 Arabic letters, plus the لا and لله ligatures |
| training data | 30,807 words, 91,390 training records, and 1,150 shapes |

### Beyond This Model

The network above is a baseline, not a limit of the format. The .ntf file names
its model type and dimensions, so later versions can use different
architectures.

A native NeuralType font could use a small
[Transformer](https://arxiv.org/abs/1706.03762) to read a whole line or page at
once. Its attention layers would let every letter respond to the rest of the
composition. Page dimensions could also be inputs. The model could then balance
the line as a whole instead of copying Gulzar one local shape at a time.

The fixed grid could also be replaced by a continuous field. Instead of
returning all 33,945 cell values at once, the network would receive an x/y point
and return the distance at that point. The renderer could ask for more samples
around hairlines and tapers. Work on
[continuous signed-distance functions](https://arxiv.org/abs/1901.05103),
[SIREN](https://arxiv.org/abs/2006.09661), and
[Fourier features](https://arxiv.org/abs/2006.10739) shows several ways to build
this kind of coordinate-based network.

![The current distilled model uses nearby letters and returns one fixed grid per shape. A possible native model reads a whole line or page and returns the distance at any requested x/y point.](./future-architecture.png)

Diffusion is newer, but it is not an obvious fit for a font. It usually needs
many passes to produce one result. A font needs deterministic output while the
user types. The next useful experiment is a small whole-line context model with
a continuous distance-field decoder. This is a proposed direction, not part of
the current demo.

### Tracing with img2bez

The model outputs a field, but text needs outlines. The demo uses two tracers.
While you type, a fast sub-pixel tracer draws each word. When input settles,
[img2bez](/blog/img2bez) replaces it with a higher-quality outline. img2bez is a
Rust crate I built specifically for tracing AI-generated glyph images. It finds
the edge, fits bézier curves to it, and produces an outline that can be used in
a font. Its settings can favor accuracy, smoother curves, or fewer points. The
demo uses the Clean profile with a tight, faithful fit. It applies light
smoothing and uses SmoothG2 mode to keep the joins between curves smooth.

The slower tracer runs in a Web Worker, separate from the thread that handles
typing and drawing. The editor stays responsive, and each new outline appears
when ready.

For this project, I added direct distance-field input to img2bez. It traces the
model's field directly, without first turning it into a raster image.

### Failed Scaling Attempts

I tested three ways to improve the model. Increasing the field resolution made
the model larger but did not improve the letters. Widening the network made the
results worse. Training a transformer to draw outlines directly produced
fragments instead of complete shapes.

![Three words. The teacher's outlines on the left, the field model in the middle drawing them almost identically, and the vector model on the right producing only small scattered fragments.](./vector-fragments.png)

| | trainable parameters | f32 export | result |
| --- | --- | --- | --- |
| field, 64 px/em | 1,357,995 | 5.4 MB | IoU 0.945, compressed to 1.38 MB in the demo |
| field, 96 px/em | 3,101,483 | 12.4 MB | IoU 0.825, no visible gain |
| field, 64 px/em, wide | 5,357,091 | 21.4 MB | IoU 0.809, strokes merge |
| vector, outline tokens | 12,693,639 | 53.3 MB | accuracy 0.482, fragments |

The smallest model is the one used in the demo, but it is incomplete. At an IoU
of 0.945, it rounds sharp features and weakens or omits small ones. Exact
OpenType output is not the goal, and some smoothing is acceptable. The missing
detail still needs to be recovered. None of the three larger designs addressed
this problem.

The vector result is consistent with previous research.
[DeepVecFont](https://arxiv.org/abs/2110.06688) generated outlines as command
sequences but needed image-guided refinement to produce usable curves.
[DeepVecFont-v2](https://arxiv.org/abs/2303.14585) redesigned the outline
representation to make the sequences learnable.
[VecFontSDF](https://arxiv.org/abs/2303.12675) instead based vector font
synthesis on signed-distance functions, the representation used here.

The next work will also improve the data. The corpus needs more real Urdu and
Persian text. It also needs to preserve placement variants. Gulzar can place the
same local letter context differently in different words. The current training
step combines these examples and uses their average position, which may not
match any of them. A future model should keep the variants and use more context
to choose between them.

### Project Status

The current pipeline is complete, and the demo runs it end to end. Work now
focuses on a larger corpus, model quality, worst-case proof sheets, and tests
with real Urdu and Persian text. Development happens
in the [post-opentype repo](https://github.com/eliheuer/post-opentype).
The plan lives in
[docs/DISTILL.md](https://github.com/eliheuer/post-opentype/blob/main/docs/DISTILL.md).
