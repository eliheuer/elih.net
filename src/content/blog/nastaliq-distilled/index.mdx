A previous post introduced the [NeuralType (.ntf)](/blog/neuraltype) font
format. An .ntf font is a small neural network, not a system that emulates
Gutenberg's movable type with virtual rectangles. The first .ntf font was
[square Kufic](https://en.wikipedia.org/wiki/Kufic#Square_Kufic), a
style that resembles low-resolution pixel art. That font was a simple test just to see if the concept could work.
This post tests whether a neural font can reproduce a complex OpenType font and be a real alternative to to Opentype format.

I converted [Gulzar](https://github.com/googlefonts/Gulzar), an OpenType
Nasta’liq font, into a .ntf. OpenType handles Nasta’liq poorly so this seems like a good style to use for exploring this concept. The current
result is in the interactive demo below. Type, copy, paste, move the cursor with the arrow
keys, and press space to separate joined letters.

<NeuralTypeDemo {...nastaliqDemo} />

The demo runs the full pipeline in the browser. The font is a
1.36-million-parameter model stored in a 5.4 MB .ntf file. The engine is Rust
compiled to WASM and built mostly with
[Linebender](https://linebender.org/) crates.

Distillation of existing OpenType fonts tests whether the format works. It also gives early estimates of the required parameter count and file size. The longer-term goal is to design
new fonts for the format that can do things OpenType cannot.

Nasta’liq is a relativly non-linear style of the Perso-Arabic script. In
calligraphy form, composition if relativly freeform. A calligrapher can stack words, extend strokes, and adjust the positions of letters and dots to balance the black and white space.

![A calligraphic composition by Mishkín-Qalam.](./mishkin-qalam-48.jpg)
<p class="img-credit">Calligraphy by <a href="https://en.wikipedia.org/wiki/Mishk%C3%ADn-Qalam">Mishkín-Qalam</a> (1826–1912). Public domain, via <a href="https://commons.wikimedia.org/wiki/File:Mishkin-Qalam-48.JPG">Wikimedia Commons</a>.</p>

An OpenType Nasta’liq font turns these choices into predefined glyphs and
shaping rules. OpenType can select contextual forms and move each glyph in both
axes, so it can reproduce the descending connections. But OpenType shaping does
not make new compositional decisions from the outlines or the available page
space. The font designer must anticipate contexts and encode the alternatives,
positioning, and collision fixes.

### Measuring Gulzar

The first step is to measure the problem: how much contextual
behavior does Gulzar contain?

I shaped every two-letter word in Gulzar with
[harfrust](https://github.com/harfbuzz/harfrust) and counted how
many glyphs each letter uses at the start of a word. The form varies with the
following letter. Gulzar uses 16 initial forms for ن, 15 for ي, and 14 for م.
Across all 31 letters, it uses 344 distinct word-initial glyphs. Amiri, a Naskh
font with rich contextual behavior, uses 150 in the same test.

The figure below shows initial ن in green, with the following
letter in gray. The follower selects the shape.

![Fourteen ordered pairs. The green word-initial ن takes a different shape for each gray follower.](./noon-variants.png)

The figure below shows the word نستعليق shaped by Gulzar. Glyphs reach **1.38 em above the baseline**. The word spans more than a full em of vertical travel. The
letters alternate between green and gray, and the gray rule marks the baseline.
Each red dot is an attachment point where Gulzar places one letter relative to
the previous letter. The red line connects the points in writing order. The
model must learn the offset between each pair of points.

![The word Nasta’liq shaped by Gulzar: letters step down from high above the baseline, and the final swash lands below it.](./cascade.png)

### Extraction

Distillation needs a teacher, a working system whose output the new model can
copy. The teacher is not the Gulzar font file alone. It is Gulzar plus
HarfBuzz, the shaping engine that reads text, consults the font's rule tables,
and returns glyphs and positions.

The same text always produces the same result, and shaping one word takes a
fraction of a millisecond. The extraction tool can therefore generate as much
training data as needed.

The
[`crates/neuraltype-distill`](https://github.com/eliheuer/post-opentype/tree/main/crates/neuraltype-distill)
extraction tool shapes every one-, two-, and three-letter word, for a total of
30,783.
Three-letter words are the shortest strings in which a letter has a neighbor on
both sides. These contexts produce medial forms. A second pass added 24 real
words from the bismillah and the
surahs Al-Fatiha and Al-Ikhlas, plus the word نستعليق. The full corpus contains
30,807 words.

The corpus also explains the demo's limits. Longer words can contain letter
contexts absent from the training data, so the model must guess and often
renders them poorly. A larger corpus of real Urdu and Persian text should
reduce these failures.

For each letter, the tool records its complete shape, including dots, and its
offset from the previous letter. These offsets are the red steps in the figure
above.

The corpus contains 91,390 records and **1,150 unique letter shapes**. More
than 100 belong to خ alone.

The figure below shows every shape of خ in the dataset, 108 in
total.

![All 108 shapes of خ in the dataset, in a grid.](./kha-shapes.png)

### Signed-Distance Fields

The model has to reproduce 1,150 letter shapes from Gulzar. We could train it to
generate the bézier outlines directly, but one wrong drawing command can break
a contour. Instead, we convert each shape to a signed-distance field. The model
predicts this field, and the renderer converts it back into an outline.

In a signed-distance field, each cell stores its distance to the nearest edge
of the letter. Values are positive inside the letter and negative outside. The
edge is zero.

The figure below shows one row of the field. The red line in the left panel
marks the row. The middle panel plots its values. The curve rises as the row
enters the letter and falls as it leaves. The red dots mark the zero crossings
at the letter's edges.

The right panel magnifies one crossing. The edge does not snap to the grid. Its
position is interpolated between two neighboring cell values and can fall
anywhere between them. A low-resolution field can therefore produce a precise
outline. Errors are also local: a small error in one cell shifts the crossing
instead of breaking the contour.

![Three panels: the خ distance field with a red slice line, the slice's values as a curve crossing zero at each stroke edge, and one crossing magnified to show the edge landing between two cells.](./sdf-slice.png)

The image below shows the isolated خ from the training set. On the
left is the shape. On the right is its signed-distance field, with
the zero contour in red. The model learns to reproduce this field.

![The isolated خ from Gulzar, and the same shape as a signed-distance field with the zero contour marked in red.](./sdf-kha.png)

The next figure shows a small patch of the field cell by cell. Each cell lists
its distance in pixels: negative outside and positive inside. The red outline
passes through the interpolated zero crossings. This patch contains a thin
stroke, so the outline crosses it twice.

![A patch of the distance field enlarged to a grid of numbered cells. Values rise from negative to positive and back, and the red zero contour passes between the cells at interpolated positions.](./sdf-cells.png)

We rendered test shapes at two resolutions. At 64 pixels per em, Gulzar's
tapers and hairlines survive the threshold. At 96 pixels per em, the result
looks the same at reading size, but the model must output 2.3 times more pixels.
The model therefore uses 64 pixels per em on a shared 155×219-pixel canvas.
Nasta’liq needs this large canvas because swash tails and dots extend far from
each letter's origin.

Below is the isolated خ at both resolutions, shown at the same
size: 64 on the left, 96 on the right.

![The isolated خ thresholded at 64 and 96 pixels per em, at the same size. The two are nearly identical.](./res-64-96.png)

### Training the Student

The model reads a five-letter window: the current letter and two neighbors on
each side. Five letters are enough. Given the same window, Gulzar always draws
the same shape.

The model has three stages. First, it represents each context letter with a
short list of numbers learned during training. Second, a small network combines
the five lists into a 256-number description of the target shape. Third, five
upscaling layers turn that description into a field, doubling the image size at
each step. A separate output predicts the offset to the next letter.

The total is 1.36 million parameters, 5.4 MB stored as 32-bit
numbers. The Gulzar TTF is 963 KB.

The model card:

| Nasta’liq-gulzar .ntf, v0 (working name) |   |
| --- | --- |
| architecture | 5 context embeddings (24 dims) → MLP (120 → 256) → 5 transposed convolutions (128 → 64 → 32 → 16 → 8 → 1 channels, 4×4 kernels, stride 2) + a 2-value displacement head |
| parameters | 1,357,995 |
| file | 5,433,100 bytes: f32 weights + a 1.1 KB JSON header |
| output | one 155×219 signed-distance field at 64 px/em, plus one displacement vector |
| vocabulary | 34 tokens: 31 letters, the لا and لله ligatures, and a boundary token |
| corpus | 30,807 words from the teacher: 91,390 letter-in-context records, 1,150 composed shapes |
| teacher | Gulzar Regular shaped by HarfBuzz ([harfrust](https://github.com/harfbuzz/harfrust)) |
| optimizer | AdamW, lr 3e-4, then a 1e-4 decay pass; batch 128; every 20th record held out |
| compute | one Apple M4 Mac laptop, CPU ([candle](https://github.com/huggingface/candle) accelerate backend), about 8 minutes per epoch. Later runs moved to a Linux PC with an RTX 2060 SUPER, at 100 seconds per epoch |

Training uses [candle](https://github.com/huggingface/candle). The same code
runs on CPU, Metal, or CUDA. Inference uses plain Rust in the engine and
requires no machine-learning framework. The engine reads the weights directly.

Progress is measured with intersection over union (IoU), a standard score for
shape agreement. It divides the overlapping ink area by the total area covered
by either shape. Identical shapes score 1.0. Shapes with no overlap score 0.

Words were legible by epoch 12. Thin strokes formed last. A hairline contributes
tens of pixels to the loss, while a bowl contributes thousands, so the model
learns bowls first.

The hardest word was الله. Gulzar uses a dedicated ligature, but no word in the
first corpus was long enough to trigger it. The bismillah and other real words
added the ligature to the data. These few dozen examples had little weight in a
corpus of thirty thousand words. Repeating them dozens of times per epoch made
the ligature converge in eight epochs.

Training finished at an IoU of 0.945. A final pass with a decaying learning
rate refined the remaining details. The same schedule took the Kufic font from
almost correct to exact. The bismillah now renders more accurately, including
its ligatures.

The sheet below compares the teacher with the final model. Gulzar is

### Tracing with img2bez

The model outputs a field, but text needs outlines. The demo uses two tracers.
While you type, a fast sub-pixel tracer draws each word. When input settles,
[img2bez](/blog/img2bez) replaces it with a higher-quality outline. I built
img2bez to turn rasters into font-grade bézier curves.

The slower tracer runs in a Web Worker, separate from the thread that handles
typing and drawing. The editor stays responsive, and each new outline appears
when ready.

This pipeline added direct distance-field input to img2bez. It now traces the
model's field without an intermediate image. The fitted curves are smooth, with
no corners or kinks. The render path creates no raster image. The model outputs
a field, and img2bez converts it to curves.

### Scaling Attempts

The demo model has 1.36 million parameters. Three larger designs performed
worse for different reasons.

**More pixels.** Retraining at 96 px/em grew the model to 3.10
million parameters, but the letters looked the same. Almost all new parameters
went into the layer that seeds the larger image, not into the layers that model
letterforms. The 64 px/em field already places edges at fractional-pixel
positions, so grid resolution was not the limit.

**Wider layers.** Doubling the width of every layer gave 5.36
million parameters and reduced the score from 0.945 to 0.809. Strokes became
heavy, and letters merged where they should remain separate. The larger model
reused settings from a model one quarter its size, but training settings do not
transfer reliably across model sizes
([hyperparameter transfer](https://arxiv.org/abs/2203.03466)). Its score was
still rising when the run ended.

**Outlines instead of fields.** The third attempt predicted curve
points as a stream of drawing tokens. It used a 12.7-million-parameter
transformer similar to the
[Virtua Grotesk](/blog/virtua-grotesk) model. It never learned to
draw. Dots land near where dots belong, and fragments follow the
downward slope of the words, but strokes never close.

![Three words. The teacher's outlines on the left, the field model in the middle drawing them almost identically, and the vector model on the right producing only small scattered fragments.](./vector-fragments.png)

| | parameters | file | result |
| --- | --- | --- | --- |
| field, 64 px/em | 1,357,995 | 5.4 MB | IoU 0.945, the font in the demo |
| field, 96 px/em | 3,101,483 | 12.4 MB | IoU 0.825, no visible gain |
| field, 64 px/em, wide | 5,357,091 | 21.4 MB | IoU 0.809, strokes merge |
| vector, outline tokens | 12,693,639 | 53.3 MB | accuracy 0.482, fragments |

The smallest model still performs best, but it is incomplete. At an IoU of
0.945, it rounds sharp features and weakens or omits small ones. Exact OpenType
output is not the goal, and some smoothing is acceptable. The missing detail
still needs to be recovered. None of the three larger designs addressed this
problem.

The vector result is consistent with previous research.
[DeepVecFont](https://arxiv.org/abs/2110.06688) generated outlines as command
sequences but needed image-guided refinement to produce usable curves.
[DeepVecFont-v2](https://arxiv.org/abs/2303.14585) redesigned the outline
representation to make the sequences learnable.
[VecFontSDF](https://arxiv.org/abs/2303.12675) instead based vector font
synthesis on signed-distance functions, the representation used here.

The next work will focus on data and representation. First, extend the corpus
with real Urdu and Persian text. Second, preserve the teacher's variants. When
Gulzar draws the same context in more than one way, the training set currently
keeps only the most common shape. Third, test representations that store more
shape information per parameter, such as a model that returns the distance at
any queried point instead of a fixed grid of samples.

### Project Status

The current pipeline is complete, and the demo runs it end to end. Work now
focuses on a larger corpus, model quality, worst-case proof sheets, and tests
with real Urdu and Persian text. Development happens
in the [post-opentype repo](https://github.com/eliheuer/post-opentype).

[docs/DISTILL.md](https://github.com/eliheuer/post-opentype/blob/main/docs/DISTILL.md).
