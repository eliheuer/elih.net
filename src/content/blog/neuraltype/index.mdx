NeuralType (.ntf) is an experiment in what comes after OpenType: a font
format where the font file is a small neural network that generates
outlines, not a table of outlines. The spec, research notes, and Rust
engine are on GitHub at
[github.com/eliheuer/post-opentype](https://github.com/eliheuer/post-opentype),
dual-licensed under Apache-2.0 or MIT.

The .ntf model running in the demo below contains no glyphs. It is the
weights of a 55k-parameter neural network. Every shape on the canvas is
generated by a forward pass at the moment you type it, traced into bézier
outlines, and filled. It is still real text: click the canvas, place the
cursor, type in Arabic or Latin capitals, select, copy, and paste. The
elongation slider changes a model input, not a glyph substitution.

### 01. A Font That Is a Neural Network

An OpenType font is a compression scheme for the Latin letter: one fixed
outline per glyph, reused everywhere, in per-glyph cells that digital type
inherited from metal sorts. Arabic in its manuscript forms, naskh and
above all nastaliq, is one continuous, context-dependent stroke, and it
has never fit this system well. The OpenType workaround is thousands of
glyphs and substitution rules approximating what a hand does in one
motion.

A font is a function:

```
glyph = F(character, context, parameters)
```

OpenType approximates `F` with a finite table of outlines plus a rule
system (cmap, GSUB, GPOS) for selecting among them. Arabic gets four
contextual classes (isolated, initial, medial, final) where the written
tradition has a continuum. A .ntf font stores `F` directly, as the weights
of a small neural network. Rendering is a forward pass per glyph, per
keystroke, followed by outline extraction. Contextual forms, elongation,
and eventually optical corrections and stylistic variation are not
compiled into tables. They are behavior of one learned function with
continuous inputs.

Three consequences follow:

- **Continuous parameters.** Justification by elongation is a scalar
  input, not a substituted glyph. Any learned axis (weight, slope,
  formality) works the same way: variable fonts without masters.
- **Open-ended context.** The conditioning vector can grow to include
  neighboring letters, position in the word, or line-fitting pressure.
  Contextual forms are not enumerated; they are generated.
- **A small, uniform file.** No table graph, no rule bytecode: a JSON
  header and a weight blob. The font in the demo is 215 KB of `f32`
  weights, before any quantization.

"Generative" here does not mean stochastic. `F` is a deterministic
function, and the same text at the same parameters renders identically
everywhere. The shapes are computed, not retrieved.

### 02. Why Square Kufic First

The first style target was going to be naskh, but square Kufic is the
right first step because its letterforms live on a coarse binary grid.
Strokes are one cell wide, counters are one cell, and the classic
reference charts for the style are pixel charts of the four contextual
forms. A glyph is an occupancy grid, so the generative representation is
trivial and every part of the pipeline stays inspectable, while the
central claims (no glyph tables, context as input, elongation as a
parameter) still hold. This is the same principle as
[Virtua Grotesk](/blog/virtua-grotesk): when the drawing lives on a grid,
the sources are machine-legible, and the design project is also a
data-engineering project.

Square Kufic is a thousand-year-old discipline from architectural
brickwork (*banna'i*) epigraphy, and it has real composition rules. One of
them: letters in a word may touch **only along the baseline connection**;
everywhere else, strokes keep a one-cell gap. My first letterform set
violated this and let a ح fuse with a following م into an unreadable
shape. The fix is an invariant of the letterform data: the edge column of
any joined side may contain only the baseline cell.

### 03. How It Works: Teacher, Student, Tracer

The engine is Rust on the [Linebender](https://linebender.org/) stack,
compiled to WASM for the demo above. The pipeline has four stages:

1. **Shape.** Unicode text becomes joining forms, by the standard Arabic
   joining rules (the right-joiners ا د ذ ر ز و never take initial or
   medial forms). Shaping also fuses ل + ا into the mandatory لا ligature
   before the model runs, and the engine's cluster map splits the
   ligature's width across both source characters, so the cursor works
   inside it.
2. **Generate.** One forward pass per glyph. The input is a one-hot letter
   identity, a one-hot joining form, and an elongation scalar: 63 floats.
   The output is a 16×14 occupancy grid. There is no advance-width output;
   the pen moves to the leftmost column the model drew, so the metrics
   derive from the drawing.
3. **Layout.** The pen composites every generated glyph grid into one
   line-wide bitmap. Connected letters abut, so their strokes merge and a
   joined word becomes one connected region, with a one-cell gap after
   non-connectors and a three-cell word space.
4. **Trace.** The composited line becomes bézier outlines: exposed cell
   edges, oriented with the filled side on the left, chained into closed
   loops. A connected word is traced as one continuous contour, and
   [kurbo](https://github.com/linebender/kurbo) carries the paths. The
   "vector outline" toggle in the demo shows this.

The model is trained by **distillation from a procedural teacher**. The
letterforms are authored as ASCII-art grids in the Rust source, in the
same form as a square-Kufic chart, composed with i'jam dots and kashida
elongation. A few lines of the teacher:

```rust
// Beh body (ب ت ث teeth family): open bowl; tooth when joined.
(Beh, Isolated) => art!(8, ["#...#", "#...#", "#####"]),
(Beh, Final)    => art!(8, ["#...#.", "#...#.", "######"]),
(Beh, Initial)  => art!(8, ["..#", "..#", "###"]),
(Beh, Medial)   => art!(8, [".#.", ".#.", "###"]),
```

ب, ت, ث, and the joined forms of ن and ي share that one skeleton. Dots are
generated by the model, not input to it; ب and ت are different ids whose
shared rasm the network learns in training. The full training set is every
supported (letter, form, elongation) context, 437 samples. An MLP with two
hidden layers trains on it with full-batch Adam in a few minutes on CPU
and reproduces all 437 contexts exactly. The teacher never ships. The
weights are the font.

The same alphabet also carries **Latin capitals**, in a matching grid
style at full cap height. Elongation works there too: Arabic stretches its
baseline connections, while each Latin letter declares a stretch column,
so crossbars and arms extend and stems stay one cell wide. The HELLO WORLD
sample shows this with the slider. Text direction is detected
automatically, so Arabic lines run right-to-left and Latin lines run
left-to-right, including the cursor.

### 04. The .ntf File

The format:

```
offset  size    content
0       4       magic "NTF0"
4       4       u32 LE: header length H
8       H       JSON header (format, script, style, alphabet, layer sizes)
8+H     ...     raw little-endian f32 weights, layer by layer
```

The name follows TrueType and OpenType: **NeuralType**. The format is
script-agnostic. Nothing in it knows about Arabic; the alphabet, the
conditioning features, and the output head are declared per font. Arabic
is the first target because it is where per-glyph outlines fail hardest,
not because the format is for Arabic. The project briefly had an Arabic
name and I renamed it on day one. A format that aims to replace OpenType
cannot be named for one script.

### 05. Kashida: a Parameter, Not a Glyph

Arabic justification is elongation: connections between letters stretch by
amounts the calligrapher chooses per word. OpenType's answer is U+0640
ARABIC TATWEEL, a spacer glyph inserted between letters, plus JSTF tables
that almost nothing implements. That is a discrete solution to a
continuous problem.

In NeuralType, elongation is an input dimension. In a grid style the
kashida is a whole number of cells (the model is trained at five
elongation levels per joinable form, and the engine snaps the input to
them), but the axis lives in the right place: it is an input to the
function, not an inserted character or a substitution. Drag the slider and
every connection in the line stretches together, with the letterforms
staying coherent at each step. A justification engine would drive this
input per-connection to fill a measure. It is a variable-font axis, except
the axis was learned. When the output head moves from grid cells to bézier
control points (v1, below), the same input becomes continuous.

### 06. The Road to Naskh and Nastaliq

Square Kufic proves the pipeline. The reason the format exists comes next.

**v1 is naskh, and swaps the output head.** Instead of an occupancy grid,
the model emits a stroke skeleton: anchor points with bézier handles and a
pen width per point. Outlines come from kurbo's stroke expansion, a
learned broad-nib pen over a generated centerline. This is Metafont's
model, letters as pen strokes over parametrized skeletons, with the
parameter logic learned rather than hand-programmed. The conditioning also
grows: with neighboring letter identities as inputs, بـ before ح can take
a different tooth than بـ before ي without anyone enumerating the cases.
GSUB cannot do this.

**v2 is nastaliq**, the script OpenType handles worst. Letters in a
nastaliq word step diagonally down a sloped cascade whose geometry depends
on the whole word. Existing fonts approximate this with thousands of
glyphs, cursive attachment, and collision-avoidance machinery. For a
model, the cascade position, accumulated stack height, and line pressure
are more input dimensions. The success criterion: a word like نستعليق
rendered as one descending gesture, its shape a function of the whole
word.

### 07. Editing Evidence: a Font Editor for Models

If the font is a model, the font editor changes in kind: **an OpenType
editor edits the artifact; a NeuralType editor edits evidence.** The .ntf
file is trained, not compiled, so what a designer authors, versions, and
refines are exemplars: drawings of letters in context. Export is a
training run.

Today my exemplars are ASCII-art grids in the Rust source, drawn first as
pixel-editor sketches. Even this workflow shows the pattern. When I wanted
to move the dots of ق, the fix was not to move points in an outline. It
was to add an explicit dot-anchor marker to the letterform data and
retrain. The decision now lives in the training data, for every context
the letter will ever appear in. The same inversion defines the editor:

- **No glyph overview grid.** The atomic unit is not "ب medial" in a box;
  it is ب medial in this word at this elongation. You type a line, click
  into a letter, and correct it in place, joined to its real neighbors.
  The correction is stored with its full context.
- **Axes are canvases, not masters.** A variable font is drawn at fixed
  masters and interpolated between them. Here you scrub elongation, or any
  future learned axis, to any position and draw there. Every position is
  an equally valid training sample.
- **The editor asks questions.** The model generalizes to contexts nobody
  drew, so proofing becomes active learning: the editor renders the
  contexts it is least certain of and asks for acceptance or correction.
  Design labor goes where the model is weakest.
- **Train is the new compile.** Seconds, not minutes, with fidelity
  diagnostics (this font reports 437/437 training contexts reproduced
  exactly) and visual diffs against the exemplars.

For naskh the drawing surface becomes **skeleton and pen**: a centerline
with width handles, stroke-expanded live, with the model learning
skeletons rather than outlines. This matches how calligraphy works.
Building that editor is part of the long-term plan, alongside the format;
the tools I have been building around
[Runebender](https://runebender.org) and [img2bez](/blog/img2bez) point at
the same goal.

### 08. Prior Art

Two ancestors matter most. **Metafont** (Knuth, 1979) treated letters as
programs, pen strokes over parametrized skeletons, a whole family from
about 60 parameters, and AlQalam later pushed the approach toward Qur'anic
naskh. Both show that hand-parametrization works and costs a decade of
expert authoring. That authoring cost is what a learned model replaces.
**Thomas Milo's DecoType ACE**, the engine behind Tasmeem in InDesign ME,
renders naskh from a script grammar rather than a glyph inventory. It is,
to my knowledge, the strongest existing demonstration that Arabic needs a
generative engine, not a bigger glyph table.

On the ML side there is a recent literature on learned vector glyph
synthesis (SVG-VAE, DeepSVG, Im2Vec, DeepVecFont, FontRNN) that is a
toolbox for the v1 output head. The difference in kind: those systems
generate fonts, per-glyph, context-free, offline. NeuralType generates
text setting. The model runs inside the shaping loop, conditioned on
context, at keystroke time. The closest prior work in spirit is not the
font-ML literature but ACE.

The repo's
[docs/RESEARCH.md](https://github.com/eliheuer/post-opentype/blob/main/docs/RESEARCH.md)
collects the annotated reading list, from Titus Nemeth's history of how
machine constraints deformed printed Arabic to SIL's Awami Nastaliq
engineering notes.

### 09. Early Days, and an Invitation

What exists today: a complete engine (shaping, model inference, tracing,
layout) in about 1,500 lines of dependency-light Rust, a trained
square-Kufic font covering Arabic with the لا ligature and Latin capitals,
CLI proofing tools that render teacher-vs-model comparison sheets, and the
WASM demo above. The next steps are better letterform art, a pixel-editor
importer so training data can be drawn instead of typed, weight
quantization, and the v1 naskh output head.

I think the first post-OpenType fonts will be built on grid systems like
this one, and I plan to work on that technology. If this is relevant to
you, especially if you are a calligrapher, an Arabic-script type designer,
or someone who works on complex text shaping, I want your feedback. The
repo is
[github.com/eliheuer/post-opentype](https://github.com/eliheuer/post-opentype);
issues and PRs are welcome, I'm on the
[Linebender Zulip](https://xi.zulipchat.com), and this post is itself
[a file on GitHub](https://github.com/eliheuer/elih.net/blob/main/src/content/blog/neuraltype/index.mdx),
so a suggestion can come as a PR.
