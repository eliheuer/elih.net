NeuralType (.ntf) is an experiment in what comes after OpenType: a font
format where the font file is a small neural network that generates
outlines, not a table of outlines. The spec, research notes, and Rust
engine are on GitHub at
[github.com/eliheuer/post-opentype](https://github.com/eliheuer/post-opentype),
dual-licensed under Apache-2.0 or MIT.

The .ntf model running in the demo below contains no glyphs at all. It is
the weights of a 55k-parameter neural network, and every shape on the
canvas is generated by a forward pass at the moment you type it, traced
into bézier outlines, and filled. It is still real text: click the canvas,
place the cursor, type (Arabic, or Latin capitals), select, copy, paste.
Drag the elongation slider and watch a font behave like a function.

### 01. A Font That Is a Neural Network

An OpenType font is, at heart, a compression scheme for the Latin letter:
one fixed outline per glyph, reused everywhere, boxed into per-glyph cells
that digital type inherited from metal sorts. Scripts that were never made
of boxes strain against this. Arabic in its manuscript forms, naskh and
above all nastaliq, is one continuous, context-dependent stroke, and it has
never fit the system well. The OpenType workaround is thousands of glyphs
and substitution rules faking what a hand does in one motion.

NeuralType stores the thing OpenType only approximates. A font is really a
function:

```
glyph = F(character, context, parameters)
```

OpenType approximates `F` with a finite table of outlines plus a rule
system (cmap, GSUB, GPOS) for selecting among them. Arabic gets four
contextual classes (isolated, initial, medial, final) where the written
tradition has a continuum. A .ntf font stores `F` directly, as the weights
of a small neural network. Rendering is a forward pass per glyph, per
keystroke, followed by outline extraction. Everything OpenType compiles
into tables, from contextual forms to elongation to (eventually) optical
corrections and stylistic variation, becomes behavior of one learned
function with continuous inputs.

Three consequences fall out immediately:

- **Continuous parameters.** Justification by elongation is a scalar
  input, not a substituted glyph. Any learned axis (weight, slope,
  formality) works the same way: variable fonts for free, without masters.
- **Open-ended context.** The conditioning vector can grow to include
  neighboring letters, position in the word, or line-fitting pressure.
  Contextual forms are not enumerated; they are generated.
- **A small, uniform file.** No table graph, no rule bytecode: a JSON
  header and a weight blob. The font in the demo is 215 KB of `f32`
  weights, before any quantization.

"Generative" here does not mean stochastic. `F` is a deterministic
function, and the same text at the same parameters renders identically
everywhere. It means the shapes are *computed*, not *retrieved*.

### 02. Why Square Kufic First

The first style target was going to be naskh, but square Kufic turned out
to be the right first rung on the ladder, for a reason that is obvious in
hindsight: its letterforms live on a coarse binary grid. Strokes are one
cell wide, counters are one cell, and the classic reference charts for the
style are literally pixel charts of the four contextual forms. That makes
the generative representation trivial (a glyph is an occupancy grid), so
every part of the pipeline stays inspectable while the interesting claims,
no glyph tables, context as input, elongation as a parameter, are all
still real. Readers of the [Virtua Grotesk post](/blog/virtua-grotesk)
will recognize the move: when the drawing lives on a grid, the sources
become machine-legible, and the design project becomes a data-engineering
project.

Square Kufic is also not a toy. It is a thousand-year-old discipline from
architectural brickwork (*banna'i*) epigraphy, and it comes with real
composition rules. One of them cost me a debugging session: letters in a
word may touch **only along the baseline connection**; everywhere else,
strokes keep a one-cell gap. My first letterform set let a ح fuse with a
following م into an unreadable blob. The fix became an invariant of the
letterform data: the edge column of any joined side may contain only the
baseline cell.

### 03. How It Works: Teacher, Student, Tracer

The engine is Rust on the [Linebender](https://linebender.org/) stack,
compiled to WASM for the demo above. The pipeline has four stages:

1. **Shape.** Unicode text becomes joining forms, by the standard Arabic
   joining rules (the right-joiners ا د ذ ر ز و never take initial or
   medial forms). Shaping also fuses ل + ا into the mandatory لا ligature
   before the model runs, and the engine's cluster map splits the
   ligature's width across both source characters, so the cursor still
   works inside it.
2. **Generate.** One forward pass per glyph. The input is a one-hot letter
   identity, a one-hot joining form, and an elongation scalar: 63 floats.
   The output is a 16×14 occupancy grid. There is no advance-width output;
   the pen simply moves to the leftmost column the model drew, so the
   metrics fall out of the drawing.
3. **Layout.** The pen composites every generated glyph grid into one
   line-wide bitmap. Connected letters abut, so their strokes merge and a
   joined word becomes one connected region, the way the script demands,
   with a one-cell gap after non-connectors and a three-cell word space.
4. **Trace.** The composited line becomes bézier outlines: exposed cell
   edges, oriented with the filled side on the left, chained into closed
   loops. A connected word is traced as one continuous contour, and
   [kurbo](https://github.com/linebender/kurbo) carries the paths. The
   "vector outline" toggle in the demo shows exactly this.

The model is trained by **distillation from a procedural teacher**: the
letterforms are authored as ASCII-art grids in the Rust source, exactly
like a square-Kufic chart, composed with i'jam dots and kashida
elongation. A few lines of the teacher, verbatim:

```rust
// Beh body (ب ت ث teeth family): open bowl; tooth when joined.
(Beh, Isolated) => art!(8, ["#...#", "#...#", "#####"]),
(Beh, Final)    => art!(8, ["#...#.", "#...#.", "######"]),
(Beh, Initial)  => art!(8, ["..#", "..#", "###"]),
(Beh, Medial)   => art!(8, [".#.", ".#.", "###"]),
```

Note what is *not* authored. ب, ت, ث, and the joined forms of ن and ي all
share that one skeleton. Dots are generated by the model, not input to it;
ب and ت are simply different ids whose shared rasm the network discovers
in training. The full training set is every supported (letter, form,
elongation) context, 437 samples in all. A hand-rolled MLP with two hidden
layers trains on it with full-batch Adam in a few minutes on CPU and
reproduces all 437 contexts exactly. The teacher never ships. The weights
are the font.

The same alphabet also carries **Latin capitals**, in a matching grid
style at full cap height, and elongation works there too. Arabic stretches
its baseline connections; each Latin letter instead declares a stretch
column, so crossbars and arms extend while stems stay one cell wide. One
parameter, two scripts, two completely different stretching behaviors, all
learned by the same small network. Try the HELLO WORLD sample with the
slider. Text direction is detected automatically, so Arabic lines run
right-to-left and Latin lines run left-to-right, including the cursor.

### 04. The .ntf File

The format is deliberately boring:

```
offset  size    content
0       4       magic "NTF0"
4       4       u32 LE: header length H
8       H       JSON header (format, script, style, alphabet, layer sizes)
8+H     ...     raw little-endian f32 weights, layer by layer
```

The name matters to me: TrueType, OpenType, **NeuralType**. The format is
script-agnostic. Nothing in it knows about Arabic; the alphabet, the
conditioning features, and the output head are declared per font. Arabic
is the first target because it is where per-glyph outlines fail hardest,
not because the format is for Arabic. (The project briefly had an Arabic
name and I renamed it on day one. A format that wants to replace OpenType
cannot be named for one script.)

### 05. Kashida: a Parameter, Not a Glyph

The elongation slider in the demo is the clearest single argument for the
whole idea. Arabic justification is *elongation*: connections between
letters stretch, gracefully, by amounts the calligrapher chooses per word.
OpenType's answer is U+0640 ARABIC TATWEEL, a spacer glyph you insert
between letters, plus JSTF tables that almost nothing implements. It is a
discrete, typographically wrong solution to a continuous problem.

In NeuralType, elongation is just an input dimension. In a grid style the
kashida is necessarily a whole number of cells (the model is trained at
five elongation levels per joinable form, and the engine snaps the input
to them), but the important thing is *where the axis lives*: it is an
input to the function, not an inserted character, a substitution, or an
extra glyph. Drag the slider and every connection in the line stretches
together, the letterforms staying coherent at each step. A justification
engine would drive this input per-connection to fill a measure. It is a
variable-font axis, except the axis was *learned*. When the output head
moves from grid cells to bézier control points (v1, below), the same
input becomes genuinely continuous.

### 06. The Road to Naskh and Nastaliq

Square Kufic proves the pipeline. The reason the format exists is further
up the ladder.

**v1 is naskh, and swaps the output head.** Instead of an occupancy grid,
the model emits a stroke skeleton: anchor points with bézier handles and a
pen width per point. Outlines come from kurbo's stroke expansion, a
learned broad-nib pen over a generated centerline. This is Metafont's
insight, that letters are pen strokes over parametrized skeletons, with
the parameter logic learned rather than hand-programmed. The conditioning
also grows: with neighboring letter identities as inputs, بـ before ح can
take a different tooth than بـ before ي without anyone enumerating the
cases, which is the thing GSUB fundamentally cannot do.

**v2 is nastaliq**, the script OpenType handles worst and the one a
contextual generative model is naturally shaped for. Letters in a nastaliq
word step diagonally down a sloped cascade whose geometry depends on the
whole word. Existing fonts fight this with thousands of glyphs, cursive
attachment, and collision-avoidance machinery. For a model, the cascade
position, accumulated stack height, and line pressure are just more input
dimensions, and the success criterion is simple to state: a word like
نستعليق rendered as one descending gesture, its shape a function of the
whole word, which is what nastaliq *is*.

### 07. Editing Evidence: a Font Editor for Models

If the font is a model, what does the font *editor* become? The difference
from every existing tool fits in one sentence: **an OpenType editor edits
the artifact; a NeuralType editor edits evidence.** The .ntf file is
trained, not compiled, so what a designer authors, versions, and refines
are *exemplars*: drawings of letters in context. "Export" is a training
run.

Today my exemplars are ASCII-art grids in the Rust source, with
pixel-editor sketches on the way there, and even that crude workflow shows
the shape of the thing. When I disliked where the engine placed the dots
of ق, the fix was not to move points in an outline. It was to add an
explicit dot-anchor marker to the letterform data and retrain. The
aesthetic decision now lives in the training data, permanently, for every
context the letter will ever appear in. That inversion generalizes into
what I think the editor looks like:

- **No glyph overview grid.** The atomic unit is not "ب medial" floating
  in a box; it is *ب medial in this word at this elongation*. You type a
  line, click into a letter, and correct it in place, joined to its real
  neighbors. The correction is stored with its full context.
- **Axes are canvases, not masters.** A variable font is drawn at fixed
  masters, and the interpolation is prayed over. Here you scrub elongation,
  or any future learned axis, to any position and draw there. Every
  position is an equally valid training sample.
- **The editor asks questions.** The model generalizes to contexts nobody
  drew, so proofing becomes active learning: the editor renders the
  contexts it is least certain of and asks for acceptance or correction.
  Design labor goes exactly where the model is weakest.
- **Train is the new compile.** Seconds, not minutes, with fidelity
  diagnostics (this font reports 437/437 training contexts reproduced
  exactly) and visual diffs against the exemplars.

For naskh this converges with how calligraphy actually works. The drawing
surface becomes **skeleton and pen**, a centerline with width handles,
stroke-expanded live, and the model learns skeletons, not outlines.
Building that editor is part of the long-term plan here, alongside the
format itself; the tools I've been building around
[Runebender](https://runebender.org) and [img2bez](/blog/img2bez) are
pointed at the same future.

### 08. Prior Art

The two intellectual ancestors are old and mostly ignored by the current
font stack. **Metafont** (Knuth, 1979) treated letters as programs, pen
strokes over parametrized skeletons, a whole family from about 60
parameters, and AlQalam later pushed the approach toward Qur'anic naskh.
The lesson of both is that hand-parametrization works and costs a decade
of expert authoring, which is exactly the cost a learned model amortizes.
**Thomas Milo's DecoType ACE**, the engine behind Tasmeem in InDesign ME,
renders naskh from a script grammar rather than a glyph inventory, and it
remains, to my knowledge, the strongest existing demonstration that Arabic
wants a generative engine, not a bigger glyph table.

On the ML side there is a rich recent literature on learned vector glyph
synthesis (SVG-VAE, DeepSVG, Im2Vec, DeepVecFont, FontRNN) that is a
toolbox for the v1 output head. But note the difference in kind: those
systems generate *fonts*, per-glyph, context-free, offline. NeuralType
generates *text setting*. The model runs inside the shaping loop,
conditioned on context, at keystroke time. Closest in spirit is not the
font-ML literature but ACE.

The repo's
[docs/RESEARCH.md](https://github.com/eliheuer/post-opentype/blob/main/docs/RESEARCH.md)
collects the full annotated reading list, from Titus Nemeth's history of
how machine constraints deformed printed Arabic to SIL's admirably candid
Awami Nastaliq engineering notes.

### 09. Early Days, and an Invitation

What exists today is one working rung: a complete engine (shaping, model
inference, tracing, layout) in about 1,500 lines of dependency-light Rust,
a trained square-Kufic font covering Arabic with the لا ligature and Latin
capitals, CLI proofing tools that render teacher-vs-model comparison
sheets, and the WASM demo above. The immediate next steps are better
letterform art (a few forms are serviceable rather than beautiful), a
pixel-editor importer so the training data can be drawn instead of typed,
weight quantization, and then the v1 naskh output head, where the
interesting research starts.

I think the first post-OpenType fonts will be built on grid systems like
this one, and I hope to play a part in building that technology. If any of
this is interesting to you, especially if you are a calligrapher, an
Arabic-script type designer, or someone who has fought GSUB for a living,
I would genuinely like your feedback. The repo is
[github.com/eliheuer/post-opentype](https://github.com/eliheuer/post-opentype);
issues and PRs are welcome, I'm on the
[Linebender Zulip](https://xi.zulipchat.com), and this post is itself
[a file on GitHub](https://github.com/eliheuer/elih.net/blob/main/src/content/blog/neuraltype/index.mdx),
so a suggestion can come as a PR.
